    ServiceNow Integration Strategy¶

    This document defines the strategy to add live ServiceNow support to Tech Support AI, building on the existing ticketing provider abstraction (packages/ticketing). It is intended for engineering leads, architects, and integrators planning the work.

    Status: Strategy (not yet implemented)
    Prerequisite: Provider abstraction layer (Zammad live, ServiceNow stub registered)
    Target scope (MVP): CreateTicket and CheckStatus — matching current product capabilities

    1. Executive summary¶

    Tech Support AI already routes ticket operations through a provider-neutral path:

    LangGraph ticket_tool → TicketGateway → Adapter → HTTP client → Help desk API

    ServiceNow is registered (TICKETING_PROVIDER=servicenow) but the ServiceNowAdapter returns NOT_IMPLEMENTED. Orchestration loads config/providers/servicenow/mapping.yaml, yet workflow payloads and search queries remain Zammad-shaped.

    Recommendation: Implement ServiceNow as a parallel adapter + client package, mirroring the Zammad pattern. Do not fork orchestration or the agent graph. Invest in:

    1. New packages/servicenow-client/ (HTTP + models + errors)
    2. Real ServiceNowAdapter (command → Table API mapping)
    3. Enriched ServiceNow mapping YAML (impact/urgency, assignment groups, caller lookup)
    4. Neutral search criteria in orchestration (remove Zammad query syntax from workflow)
    5. Tests at client, adapter, pipeline, and optional live-integration layers

    Default record type: incident (ITSM). Catalog requests (sc_request) are out of MVP scope unless a customer mandates them.

    2. Current state¶

    What exists today¶

    Component Zammad ServiceNow
    Factory registration Live Stub only
    TicketingSettings / env ZAMMAD_* vars No SN vars; is_configured() always True
    HTTP client package packages/zammad-client None
    Adapter CREATE_TICKET Implemented NOT_IMPLEMENTED
    Adapter SEARCH_TICKETS Implemented NOT_IMPLEMENTED
    Mapping YAML Production-ready Stub values
    Orchestration mapping load Provider-aware Works (loads SN YAML)
    Workflow command shape Zammad payload Same Zammad payload
    CheckStatus search query customer.email:… AND number:… Same Zammad syntax (wrong for SN)
    Customer ID guess:{email} Plain {email} in YAML (unused)
    ticket_tool normalization Zammad guess: prefix Applied to all providers
    Audit ZammadOperation table None
    Tests Full adapter + pipeline Stub test only
    External docs Zammad integration guide Mentioned as stub

    Key files (integration surface)¶

    Path Role
    packages/ticketing/providers/servicenow_adapter.py Replace stub
    packages/ticketing/factory.py Wire ServiceNowClient
    packages/ticketing/settings.py Add SN credentials
    config/providers/servicenow/mapping.yaml Instance-specific mapping
    packages/orchestration/workflow.py Neutralize search + optional create payload
    packages/agents/nodes/ticket_tool.py Provider-aware customer normalization
    packages/zammad-client/ Reference implementation pattern

    Design principle (unchanged)¶

    The LLM and orchestration propose and validate intents. Only the adapter translates neutral commands into ServiceNow Table API calls. Ticket numbers in the UI must come from ServiceNow responses (number field), never from the model.

    3. ServiceNow vs Zammad — conceptual mapping¶

    Concept Zammad ServiceNow (MVP: Incident)
    Ticket identity id + number sys_id + number (e.g. INC0012345)
    Title title short_description
    Description First article body description
    Customer customer_id (guess:{email}) caller_id → sys_user.sys_id
    Assignment group (name) assignment_group (name or sys_id)
    Priority Single priority label impact + urgency → computed priority
    State state state / incident_state (display values)
    Search Zammad query language Encoded query (sysparm_query)
    Auth API token (Bearer) Basic (dev) or OAuth 2.0 (prod)
    API style REST /api/v1/tickets Table API /api/now/table/incident

    New package: packages/servicenow-client/¶

    Mirror packages/zammad-client/:

    Module Responsibility
    client.py ServiceNowClient — httpx, retries, auth
    models.py CreateIncidentRequest, Incident, IncidentSearchResult, SysUser
    errors.py ServiceNowError, ServiceNowErrorCode enum

    Minimum client methods (MVP):

    Method Table API Purpose
    create_incident(request) POST /api/now/table/incident CreateTicket
    get_incident(sys_id) GET /api/now/table/incident/{sys_id} GetTicket (future)

    lookup_user_by_email(email) GET /api/now/table/sys_user?sysparm_query=email=… Caller resolution

    5. Command mapping (MVP)¶

    5.1 CREATE_TICKET¶

    Inbound payload (from orchestration today — Zammad-shaped; adapter absorbs translation):

    {
  "title": "VPN not connecting",
  "group": "Network Operations",
  "customer_id": "user@company.com",
  "priority": "3 - Moderate",
  "article": {
    "subject": "VPN not connecting",
    "body": "Cannot connect since 9am.",
    "type": "note",
    "internal": false,
    "content_type": "text/plain"
  }
}

    ServiceNowAdapter translation:

    Payload field ServiceNow field Notes
    title short_description Required
    article.body description Required
    group assignment_group Resolve name → sys_id if needed
    customer_id / email caller_id lookup_user_by_email → sys_id
    priority (label) impact, urgency Via mapping priority_to_impact_urgency
    categories / custom category Optional; from mapping

    Outbound ProviderTicket:

    ProviderTicket(
    provider="servicenow",
    external_id=incident.sys_id,
    display_number=incident.number,
    state=incident.state_display,
    group_or_queue=incident.assignment_group_display,
    priority=incident.priority_display,
    raw=incident.model_dump(),
)

    5.2 SEARCH_TICKETS (CheckStatus)¶

    Problem: Workflow today builds Zammad-specific queries:

    query_parts = [f"customer.email:{email}"]
query_parts.append(f"number:{ticket_number}")

    Solution (recommended): Refactor workflow to emit neutral search criteria:

    {
  "search_criteria": {
    "ticket_number": "INC0012345",
    "customer_email": "user@company.com",
    "search_hint": null,
    "open_only": false
  },
  "limit": 5
}

    Each adapter translates:

    Adapter Translation
    Zammad customer.email:{email} AND number:{n}
    ServiceNow number={n}^caller_id.email={email} (encoded query)

    Backward compatibility: Adapters accept legacy query string during migration; Zammad adapter keeps current behavior if search_criteria absent.

    6. Configuration¶

    6.1 Environment variables (new)¶

    TICKETING_PROVIDER=servicenow

# Instance
SERVICENOW_INSTANCE_URL=https://yourinstance.service-now.com
SERVICENOW_AUTH_MODE=basic          # basic | oauth
SERVICENOW_USERNAME=integration.user
SERVICENOW_PASSWORD=secret

# OAuth (production)
# SERVICENOW_CLIENT_ID=
# SERVICENOW_CLIENT_SECRET=
# SERVICENOW_TOKEN_URL=

# Optional
SERVICENOW_TABLE=incident           # default: incident
SERVICENOW_TIMEOUT_SECONDS=30
SERVICENOW_VERIFY_SSL=true

    Update: TicketingSettings, .env.example, apps/api/config.py, appendices/B-environment-variables.md.

    is_configured() for ServiceNow must require instance URL + valid auth credentials (remove stub “always configured”).

    6.2 Mapping YAML extensions¶

    Extend config/providers/servicenow/mapping.yaml:

    version: "1.0"

# Existing: priorities, groups, categories, default_group, default_priority

# NEW: map canonical priority labels → ServiceNow impact / urgency
priority_to_impact_urgency:
  "4 - Low":
    impact: "3"      # Low
    urgency: "3"     # Low
  "3 - Moderate":
    impact: "2"
    urgency: "3"
  "1 - Critical":
    impact: "1"      # High
    urgency: "1"     # High

# NEW: assignment group resolution
assignment_groups:
  # Prefer sys_id in production; names work with lookup API
  "Network Operations": "sys_id_or_name"
  "Application Support": "sys_id_or_name"

customer_lookup:
  strategy: email_to_sys_user    # email_to_sys_user | caller_id_direct
  customer_id_pattern: "{email}"

# NEW: optional category → ServiceNow category label
category_labels:
  network: "Network"
  software: "Software"

search:
  default_open_query: "active=true^ORDERBYDESCopened_at"
  max_results: 5

    Orchestration FieldMappingConfig may need optional SN-specific sections (loaded but ignored by Zammad).

    7. Authentication strategy¶

    Environment Auth mode Notes
    Personal Developer Instance (PDI) Basic Username/password integration user
    Enterprise sandbox OAuth 2.0 client credentials Preferred for production
    Enterprise production OAuth 2.0 + MID server (optional) If instance blocks direct API

    Security requirements:

    • Credentials server-side only (never in mapping YAML or browser)
    • Integration user with minimum roles: incident_manager or scoped custom role
    • sn_incident_write, sn_incident_read as needed
    • No admin roles on integration account

    8. Implementation phases¶

    Phase 0 — Discovery & sandbox (1–2 days)¶

    Task Output
    Provision ServiceNow PDI or customer sandbox Instance URL
    Create integration user + ACL verification Test credentials
    Confirm record type (incident vs sc_req_item) Written decision
    Document assignment groups, impact/urgency values Updated mapping.yaml
    Smoke-test Table API with curl/Postman Baseline requests

    Exit criteria: Manual incident create + search by number works via REST.

    Phase 1 — servicenow-client package (3–5 days)¶

    Task Details
    Scaffold packages/servicenow-client/ pyproject.toml, workspace member
    Implement ServiceNowClient httpx async, timeout, retries on 502/503/504
    Implement auth Basic first; OAuth interface stub
    Models Pydantic v2 for incident create/response
    Errors Map 401/403/404/429 to ServiceNowErrorCode
    Unit tests respx mocks for create, search, user lookup

    Exit criteria: pytest packages/servicenow-client green; no dependency on ticketing package.

    Phase 2 — ServiceNowAdapter MVP (3–4 days)¶

    Task Details
    Inject ServiceNowClient + mapping config Constructor or settings-backed
    Implement CREATE_TICKET Payload translation + caller lookup
    Implement SEARCH_TICKETS Encoded query from search_criteria or legacy fields
    Set capabilities().supports_status_search = True UI parity with Zammad
    Factory wiring build_ticket_gateway() builds client + adapter
    Settings SN env vars + configuration_error()
    Unit tests Adapter with mocked client

    Exit criteria: Adapter tests pass; factory returns configured adapter when TICKETING_PROVIDER=servicenow.

    Phase 3 — Orchestration neutralization (2–3 days)¶

    Task Details
    Refactor _check_status_command() Emit search_criteria object
    Update ZammadAdapter._search_tickets Build Zammad query from search_criteria
    Update ServiceNowAdapter._search_tickets Build sysparm_query from search_criteria
    Optional: customer_id_for_email provider branch SN returns plain email; Zammad returns guess:{email}
    Extend FieldMappingConfig Optional SN sections (impact/urgency map)
    Update orchestration tests Both providers

    Exit criteria: Same CheckStatus intent works against Zammad and ServiceNow without workflow forks.

    Phase 4 — Agent & API integration (1–2 days)¶

    Task Details
    ticket_tool.py Apply normalize_customer_id only when provider == zammad
    Populate ProviderTicket.state / group_or_queue in SN adapter Richer status cards
    TicketPipeline Verify create + search with SN (CLI path)
    apps/api startup _configure_ticketing_from_settings() passes SN settings

    Exit criteria: E2E chat flow creates incident and checks status with TICKETING_PROVIDER=servicenow.

    Phase 5 — Testing & CI (3–4 days)¶

    Layer Approach
    Client unit tests respx against Table API paths
    Adapter unit tests Mock client; assert field mapping
    Orchestration tests Neutral search criteria for both providers
    API pipeline tests test_ticket_pipeline.py parametrized by provider
    E2E (optional) Wiremock SN mappings in e2e/wiremock/
    Live integration tests/integration/ marker @pytest.mark.live_sn

    Wiremock example endpoints:

    • POST /api/now/table/incident
    • GET /api/now/table/incident
    • GET /api/now/table/sys_user

    Exit criteria: CI runs SN unit tests without credentials; live tests documented in .env.example.

    Phase 6 — Documentation & operations (1–2 days)¶

    Deliverable Location
    ServiceNow integration guide docs/external/06-integration-guide-servicenow.md (new)
    Update capability matrix docs/external/appendices/C-capability-matrix.md
    Update solution architecture docs/external/03-solution-architecture.md
    Env vars appendix appendices/B-environment-variables.md
    MkDocs nav entry mkdocs.yml
    Postman / collection SN folder docs/postman/ or SN requests in existing collection

    Phase 7 — Audit & observability (optional, parallel)¶

    Task Details
    Generalize ZammadOperation → ProviderOperation Add provider column; migration
    AuditService.record_provider_operation() Replace record_zammad()
    Wire audit into ChatService.send_message Today audit is CLI-only
    Structured logs provider=servicenow, operation, duration_ms

    9. Post-MVP roadmap¶

    Aligned with existing product backlog:

    Intent / feature ServiceNow API approach
    UpdateTicket PATCH /api/now/table/incident/{sys_id}
    AddArticle POST /api/now/table/sys_journal_field (work notes)
    AddAttachment Attachment API + table_name/table_sys_id
    EscalateTicket Update priority, urgency, or assignment group
    CloseTicket Set state to resolved/closed + close notes
    Catalog requests sc_request + requested_for flow (separate adapter methods)
    CMDB linkage Optional cmdb_ci on incident from asset hints

    10. Risks and mitigations¶

    Risk Impact Mitigation
    Zammad-shaped workflow payloads SN adapter complexity Adapter translation layer; later neutral create_payload schema
    Caller email not in sys_user Create fails Pre-flight lookup; user-facing “contact your admin” message; optional auto-provision (off by default)
    Assignment group name mismatch Wrong queue Prefer sys_id in mapping; validation script
    Impact/urgency vs priority label Wrong priority Explicit mapping table in YAML; unit tests per label
    Instance OAuth variance Auth failures Support basic for dev; document OAuth setup per customer
    Rate limiting / transaction quotas Flaky E2E Retries + backoff; respect Retry-After
    Multi-tenant instances Wrong domain data SERVICENOW_INSTANCE_URL per deployment; no cross-instance logic

    11. Key decisions (require sign-off)¶

    # Decision Recommendation Alternative
    D1 Record type Incident sc_request for service catalog
    D2 Search refactor Neutral search_criteria Duplicate workflow per provider
    D3 Auth for MVP Basic on PDI/sandbox OAuth only (slower setup)
    D4 Caller resolution Lookup sys_user by email Pass email in custom field (non-standard)
    D5 Assignment group Name with API lookup sys_id only in mapping
    D6 Client package Separate servicenow-client Inline httpx in adapter
    D7 Audit table Generalize to provider_operations Separate servicenow_operations table

    12. Acceptance criteria (MVP)¶

    • [ ] TICKETING_PROVIDER=servicenow with valid credentials passes configuration_error() == None
    • [ ] Chat CreateTicket creates an incident; UI card shows ServiceNow number (e.g. INC…)
    • [ ] Chat CheckStatus finds incident by number; status card shows state and assignment group
    • [ ] Multi-match and no-match flows behave like Zammad (disambiguation / ask for number)
    • [ ] Orchestration rejection still prevents any ServiceNow API call
    • [ ] Unit tests cover client + adapter without live instance
    • [ ] Zammad regression tests remain green
    • [ ] External integration guide published
    • [ ] No ServiceNow credentials in repo, mapping, or client-side code
