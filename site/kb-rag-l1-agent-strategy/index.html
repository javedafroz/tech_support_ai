    KB / RAG L1 Agent Strategy¶

    This document defines the strategy to add Handbook KB + RAG troubleshooting to Tech Support AI before ticket creation. It is intended for engineering leads, architects, and product owners planning the work.

    Status: Strategy — decisions locked (§16) · Phase 0 done · Phase 1 ingest/admin upload implemented · Phase 2 graph troubleshoot implemented
    Prerequisite: LangGraph support_graph (conversation → orchestrate → ticket_tool → respond); packages/storage S3-compatible client (target: Ceph RGW)
    Target scope (MVP): Retrieve from Agent Handbook → guide user through troubleshooting steps (user performs actions) → deflect or create ticket with full chat transcript + attempted steps

    1. Executive summary¶

    Today the agent is an intake + triage bot: once enough detail exists, it proposes CreateTicket and creates a Zammad ticket. It does not consult knowledge before escalating.

    Goal: Turn the agent into a true L1 support agent:

    Understand issue
  → Search Agent Handbook (RAG via Qdrant)
  → Guide the user through troubleshooting steps (user takes all actions)
  → If resolved → close without ticket (deflection)
  → If not resolved → CreateTicket with enriched description
       (symptoms + steps tried + full chat transcript)

    Locked approach:

    1. Extend LangGraph with a dedicated troubleshoot stage.
    2. Store handbook source files in Ceph RGW only (S3-compatible API) — not MinIO. Accept PDF and Markdown; convert PDF → Markdown with Docling before indexing.
    3. Index chunks in Qdrant (dedicated vector DB).
    4. Keep document metadata and ingest jobs in PostgreSQL.
    5. Ship a separate Admin SPA (apps/admin) for handbook CRUD and re-indexing.
    6. Authenticate admin users via Keycloak (OIDC Authorization Code + PKCE); enforce realm roles on admin API.
    7. No category allow-list — any CreateTicket candidate may enter troubleshoot when KB is enabled.
    8. On escalate, attach the full chat transcript (with secret redaction), not an LLM summary.

    Do not let the LLM call Zammad, Ceph, or Qdrant directly — keep orchestration as the gate for ticket actions. The agent guides; the user performs every remediation step. End-user chat auth remains unchanged for MVP (dev header / existing JWT); Keycloak is required for admin only.

    Design principle (unchanged): LLM for language and presenting grounded steps; deterministic Python for retrieval, policy, storage, and ticket execution.

    Auth (dev / JWT for chat) Admin uses Keycloak OIDC + realm roles (separate from chat)

    3. Target user flows¶

    3.1 Operating model — guide, don’t act¶

    The agent never performs remediations (no AD unlock, no remote commands, no clicking on the user’s device). It:

    1. Retrieves relevant handbook content.
    2. Presents the next step in plain language.
    3. Waits for the user to say what happened.
    4. Advances, retries, or escalates based on the user’s report.

    The user remains in control of every action.

    3.2 Happy path — resolved without ticket¶

    1. User: "VPN disconnects every 30 seconds"
2. Agent gathers minimal symptoms (device, client, error) if missing
3. Agent retrieves top handbook chunks (e.g. AnyConnect DPD timeout)
4. Agent presents Step 1 and asks the user to try it
5. User performs the step, then reports: "That fixed it"
6. Agent confirms resolution; records deflection event; no Zammad call

    3.3 Escalation path — ticket with full transcript¶

    1–4. Same as above (retrieve + present steps; user acts)
5. User: "Still failing" / steps exhausted / user asks for ticket
6. Agent (optional MVP+): confirm-before-submit summary card
7. CreateTicket description includes:
   - User problem narrative
   - Handbook article(s) consulted (title + id)
   - Steps presented + user-reported outcomes
   - Full chat transcript (redacted)
8. Ticket routed via existing category → group mapping

    3.4 No KB match¶

    1. Retrieval confidence below threshold or empty results
2. Skip troubleshoot loop; proceed to CreateTicket
3. Description notes "No matching handbook article"
4. Full chat transcript still included

    3.5 When troubleshoot runs¶

    Condition Enter troubleshoot?
    KB_RAG_ENABLED=true and intent is CreateTicket candidate Yes (all categories — no allow-list)
    CheckStatus, updates, cancel, etc. No — bypass
    KB_RAG_ENABLED=false No — today’s graph only

    5. Technology choices¶

    5.1 Object storage — Ceph RGW only (locked)¶

    Decision: Handbook source files live in Ceph Object Gateway (RGW) in every environment (dev, CI, production). Do not use MinIO for Agent Handbooks.

    Env Backend Bucket
    Local / CI Ceph RGW endpoint (shared sandbox or team-provided) agent-handbooks
    Production Ceph RGW agent-handbooks
    Unit tests In-memory ObjectStorage fake (STORAGE_BACKEND=memory) N/A — no real object store

    Why not MinIO: MinIO is only an S3-compatible stand-in; this project standardizes handbook storage on Ceph so paths, IAM, and ops match production. Chat attachments elsewhere in the repo may still use other backends; KB/handbook storage must not depend on MinIO.

    Implementation notes:

    • Reuse packages/storage S3/boto3 client with Ceph RGW endpoint_url, access key, and secret (RGW S3 API).
    • Prefer dedicated settings (CEPH_RGW_* / KB_HANDBOOK_S3_*) so handbook credentials are not shared with any attachment MinIO config.
    • Object key convention: handbooks/{org_id}/{document_id}/v{version}/{filename}
    • Store checksum (SHA-256) in metadata for integrity and skip-reindex if unchanged.
    • Handbooks are not served directly to end users; admin downloads via signed URL or API proxy.
    • Compose for KB work: do not add a MinIO service for handbooks; document required CEPH_RGW_ENDPOINT (and credentials) for local admin/ingest.

    5.2 Vector store — Qdrant (locked)¶

    Decision: Use Qdrant as the vector database from day one.

    Concern Approach
    Local / CI qdrant/qdrant service in Docker Compose
    Production Managed Qdrant Cloud or self-hosted Qdrant cluster
    Client Official qdrant-client (Python) behind packages/knowledge
    Collection agent_handbook (name configurable)
    Point id Stable UUID per chunk (same as logical chunk id)
    Payload document_id, chunk_index, title, section_title, body, category_tags, status, embedding_model, version
    Filters status=published (and optional org_id later)

    Postgres remains the system of record for documents and jobs; Qdrant is the system of record for searchable chunks. On reindex, delete-by-document_id filter then upsert new points.

    Abstract behind KnowledgeStore protocol in packages/knowledge so tests can use an in-memory fake without running Qdrant.

    5.3 Embeddings¶

    Option Notes
    OpenAI text-embedding-3-small Fits current OpenAI usage; simple
    Azure OpenAI embeddings When LLM_PROVIDER=azure_openai
    Local / open model Later cost/privacy option

    Decision: Use the same provider family as chat where possible; configure via EMBEDDING_MODEL / provider settings. Store embedding model id on each Qdrant point (and on kb_documents) so re-embed is explicit when the model changes. Collection vector size must match the model.

    5.4 PDF → Markdown conversion — Docling (locked)¶

    Decision: The system accepts PDF handbook uploads. Before chunking/indexing, convert PDF to Markdown with Docling (IBM Research, MIT-licensed, open source).

    Tool considered Why not primary
    Docling Selected — strong structure for RAG, MIT license, CPU-capable, Markdown export
    Marker High fidelity but heavier GPU bias and more restrictive model licensing for commercial use
    pymupdf4llm Fast/light for simple digital PDFs; weaker on tables/complex layout / scans
    unstructured / pypdf Adequate extractors; not best-in-class Markdown structure for handbooks

    Pipeline rule:

    PDF upload → store original in Ceph
           → Docling convert → Markdown
           → store derived Markdown in Ceph (sidecar)
           → chunk Markdown → embed → Qdrant

    Also accept native .md uploads (skip conversion). DOCX/HTML are out of MVP unless needed later.

    Ops notes:

    • Run Docling in the ingest worker (same process MVP; dedicated worker if CPU-heavy).
    • Persist converter version (docling==x.y.z) on kb_documents / ingest job for reproducibility.
    • On conversion failure → job failed with error; do not publish; allow admin retry.
    • Optional admin preview: show derived Markdown before publish.
    • Scanned/image PDFs: rely on Docling’s OCR/layout path; document quality expectations for operators.

    5.5 Chunking¶

    Parameter Default Override Rationale
    Input Markdown (native upload or Docling output) — Single chunking path
    Strategy page (one chunk per PDF page) KB_CHUNK_STRATEGY=page\|heading Keeps a page's context intact; markdown without page markers falls back to headings
    Chunk size (max chars) 4000 KB_CHUNK_MAX_CHARS Oversized pages are windowed to this cap
    Overlap (chars) 200 KB_CHUNK_OVERLAP_CHARS Continuity across windowed boundaries
    Metadata per chunk document_id, title, section_title, page, category_tags — Citations + optional payload filters

    Page markers: the Docling worker exports Markdown with a <!-- docling-page-break --> marker (via export_to_markdown(page_break_placeholder=...), with a fallback for older docling builds). The chunker splits on this marker for the page strategy.

    Canonical searchable text is always Markdown — never chunk raw PDF bytes.

    6. LangGraph changes¶

    6.1 Extended topology¶

    START → conversation
            │
            ├─ (clarify / CheckStatus / non-create) ──────────────► respond
            │
            └─ (CreateTicket candidate, KB enabled)   # all categories
                    ▼
              troubleshoot
                    │
                    ├─ needs_user_step_outcome ───────────────────► respond
                    ├─ resolved_without_ticket ───────────────────► respond
                    ├─ escalate_to_ticket ────────────────────────► orchestrate → ticket_tool → respond
                    └─ no_kb_match ───────────────────────────────► orchestrate → ticket_tool → respond

    6.2 New / extended state fields¶

    Add to SupportGraphState (and Redis session context for multi-turn):

    Field Purpose
    troubleshoot_status idle | retrieving | guiding | resolved | escalate | skipped
    retrieved_chunks Top-k hits (id, title, excerpt, score)
    active_runbook_id Current handbook document
    active_step_index Which step the user is on
    steps_attempted List of {step, instruction, user_outcome}
    kb_citations Stable refs for ticket body and audit
    resolution_outcome resolved | unresolved | user_requested_ticket

    6.3 troubleshoot node responsibilities¶

    1. If insufficient symptoms → set clarification (or rely on conversation first).
    2. Embed query from synthesized problem text; retrieve top-k from Qdrant (published only). No category allow-list — do not gate entry by suggested category.
    3. If score < threshold → skipped / escalate path.
    4. If guiding: select next step from retrieved runbook content (structured sections preferred). Present the step to the user; do not execute it.
    5. On user reply interpreting outcome (worked / failed / unclear / “create a ticket”): advance, retry, or escalate.
    6. Cap steps (e.g. max 3–5) and max turns in troubleshoot mode to avoid loops; always offer “create a ticket.”
    7. On escalate: build enriched description including full transcript; set/refresh CreateTicket intent → route to orchestrate.

    Important:

    • Retrieval and step progression are tool/code paths.
    • The LLM may phrase the step and interpret the user’s outcome report.
    • It must not invent procedures absent from retrieved content (grounding rule).
    • It must not claim to have performed an action on the user’s behalf.

    6.4 Feature flag¶

    KB_RAG_ENABLED=false          # master switch
KB_RETRIEVAL_TOP_K=5
KB_MIN_SCORE=0.72             # tune empirically
KB_MAX_TROUBLESHOOT_STEPS=5
KB_INCLUDE_CHAT_TRANSCRIPT_IN_TICKET=true

    When KB_RAG_ENABLED=false, graph behavior remains identical to today.

    7. Ticket enrichment (escalation payload)¶

    When creating a ticket after failed troubleshooting (or no KB match), the description (Zammad article body) should be structured as follows.

    Decision (locked): include the full chat transcript, not an LLM summary.

    ## Problem
VPN disconnects after ~30s with DPD timeout on Cisco AnyConnect (macOS 14).
Started yesterday; cannot reach internal tools.

## Handbook consulted
- VPN / AnyConnect DPD Timeout (doc_id=kb_018, v3)

## Steps presented (user-performed)
1. Quit AnyConnect and clear VPN cache — User reported: did not help
2. Reinstall AnyConnect profile — User reported: still disconnects

## Full conversation transcript
[user] VPN disconnects every 30 seconds
[assistant] When did this start, and do you see an error?
[user] Yesterday — DPD timeout
[assistant] Please try step 1: …
[user] Still failing
…

    Rules:

    • Ticket number still comes only from Zammad.
    • Run a redaction pass before attach (passwords, tokens, API keys, obvious secrets).
    • Include all user/assistant turns for the session (system “thought” labels may be omitted).
    • If transcript length risks provider limits, truncate oldest turns after problem + steps sections, and note truncation — do not replace with a summary.
    • Attach kb_citations in audit log even if not shown in UI.
    • Label steps as presented / user-reported outcomes so L2 knows the agent did not execute them.

    8. Admin module (separate SPA — locked)¶

    8.1 Scope¶

    A dedicated Admin application (apps/admin) for knowledge operators (IT content owners), not end users. Do not embed admin in apps/web.

    Capability MVP Later
    List / search documents ✅
    Upload handbook file → Ceph (PDF or Markdown) ✅
    PDF → Markdown via Docling (preview + store) ✅
    Edit metadata (title, categories, tags, locale) ✅
    Publish / unpublish ✅
    Trigger reindex / view job status ✅
    Preview retrieval (query sandbox against Qdrant) ✅
    Review / lightly edit derived Markdown ✅ ✅ richer editor
    In-browser Markdown editor ✅
    Version diff / rollback ✅
    Multi-tenant org isolation UI ✅
    Analytics (deflection by article) ✅

    8.2 Suggested layout¶

    apps/
  admin/          # React + Vite admin SPA (separate from apps/web)
apps/api/
  routers/admin/  # /api/v1/admin/kb/*
packages/
  knowledge/      # ingest, retrieve, models, Qdrant store

    Why separate from apps/web: different audience, authz, UX density, and release cadence. Share design tokens only if useful; do not mix composer/chat into admin.

    Method Path Purpose

    POST /api/v1/admin/kb/documents Create metadata + upload
    GET /api/v1/admin/kb/documents/{id} Detail

    8.4 Authentication & authorization — Keycloak (locked)¶

    Decision: Admin login is via Keycloak (OpenID Connect). Do not use chat X-User-Id / AUTH_MODE=dev for admin routes.

    Flow¶

    Admin SPA
  → redirect to Keycloak login (Authorization Code + PKCE)
  → receive access token (+ refresh token)
  → call /api/v1/admin/kb/* with Authorization: Bearer <access_token>
API
  → validate JWT signature via Keycloak JWKS
  → check issuer, audience/client, expiry
  → authorize by realm role (or client role) claims

    Realm / roles (suggested)¶

    Keycloak role Access
    (none / end user) Chat only — no admin routes
    kb_editor Create/update handbooks, reindex, retrieval preview
    kb_admin Everything kb_editor has + publish, delete, archive, config

    Map roles from the access token (realm_access.roles or client roles under the admin client). Prefer realm roles for MVP simplicity.

    Local / Compose¶

    Item Approach
    Keycloak service Add to Docker Compose (dev realm import)
    Clients tech-support-admin (public SPA, PKCE); optional tech-support-api for audience
    Seed users e.g. kb-editor@local / kb-admin@local in realm JSON
    Chat UI Unchanged — does not require Keycloak in MVP

    Production¶

    • Enterprise Keycloak (or org-hosted) realm
    • HTTPS only; short-lived access tokens; refresh in SPA
    • Restrict admin CORS to admin origin
    • Optional: require MFA at Keycloak for kb_admin

    Never expose /api/v1/admin/* behind open X-User-Id trust. If Keycloak is unreachable, admin is unavailable (fail closed) — chat may continue.

    Column Notes

    Note: There is no kb_chunks table with embeddings in Postgres. Chunk vectors live in Qdrant.

    9.2 Qdrant collection¶

    Setting MVP default
    Collection agent_handbook
    Distance Cosine
    Vector size Match embedding model (e.g. 1536 for text-embedding-3-small)
    Payload index document_id, status, org_id (when used)

    On document delete/unpublish: delete points by document_id filter (and/or set payload status and filter at query time — prefer delete on unpublish for simplicity in MVP).

    10. Ingest pipeline¶

    Admin upload (PDF or Markdown)
  → put original object to Ceph (agent-handbooks)
  → insert/update kb_documents (draft)
  → on Publish or Reindex:
       create kb_ingest_jobs
       → download original from Ceph
       → if PDF:
            Docling.convert → Markdown
            put derived Markdown to Ceph (sidecar key)
         if Markdown:
            use as-is
       → chunk Markdown (heading-aware)
       → embed
       → delete existing Qdrant points for document_id
       → upsert new points
       → mark job succeeded; set embedding_model, chunk_count,
         converter_name/version, derived_markdown_object_key

    MVP execution: run Docling + ingest inline or background task in API process.
    Phase 2: dedicated worker when PDF conversion is CPU-heavy or queue depth grows.

    Idempotency: same original checksum + same embedding model + same Docling version → skip. Embedding or converter version change → full reconvert/re-embed as needed.

    Object keys (example):

    handbooks/{org}/{document_id}/v{n}/source.pdf
handbooks/{org}/{document_id}/v{n}/derived.md
handbooks/{org}/{document_id}/v{n}/source.md

    11. Retrieval API (runtime)¶

    packages/knowledge exposes something like:

    retrieve(query: str, *, top_k, min_score) -> list[ChunkHit]

    Used by the troubleshoot node and admin preview. Category tags may appear in payload for ranking/debug, but must not gate whether troubleshoot runs.

    Grounding policy:

    • Steps presented to the user must be attributable to ChunkHits.
    • If ungrounded → escalate or clarify — do not invent fixes.
    • Never imply the agent executed a step.
    • Citations in thought stream / optional UI “Sources” chip (MVP+: nice-to-have).

    12. Security & compliance¶

    Topic Approach
    Handbook sensitivity Treat as internal; Ceph private bucket; no public ACLs
    Admin auth Keycloak OIDC; JWT validation + role checks; fail closed if IdP down
    Token handling Access tokens in memory (SPA); no admin tokens in chat app
    PII / secrets in tickets Mandatory redaction before attaching full transcript
    Transcript volume Full transcript by policy; redact first; truncate oldest only if provider limit
    Prompt injection via KB Sanitize retrieved text; never execute handbook content as tools
    Qdrant access Network-private; API key if exposed; no end-user direct access
    Audit Log retrieve document ids, escalate decisions, admin mutations
    Retention Soft-delete docs; deindex Qdrant; align with org policy

    13. Observability & success metrics¶

    Metric Why
    Deflection rate % sessions resolved without ticket
    Escalation after N steps Tune max steps / content quality
    Retrieval hit rate % CreateTicket candidates with ≥1 chunk above threshold
    Mean time to resolve (chat) L1 speed
    Ticket quality score (human) Did L2 find steps + transcript useful?
    Ingest job failure rate Content pipeline health
    Qdrant latency / errors Runtime retrieve health

    Emit structured logs for: kb.retrieve, kb.step_presented, kb.user_outcome, kb.resolved, kb.escalate.

    14. Phased delivery¶

    Phase 0 — Foundations (1–2 sprints)¶

    • packages/knowledge skeleton + KnowledgeStore protocol
    • Qdrant in Docker Compose + collection bootstrap
    • Ceph RGW handbook bucket wiring (dedicated settings; no MinIO)
    • Keycloak in Docker Compose + realm export (clients, kb_editor / kb_admin roles, seed users)

    16. Decisions (locked)¶

    # Topic Decision
    1 Vector DB Qdrant
    2 Admin app Separate SPA (apps/admin)
    3 Admin login Keycloak (OIDC Authorization Code + PKCE); realm roles kb_editor / kb_admin
    4 Authoring / ingest formats PDF and Markdown; PDF converted to Markdown with Docling before chunking
    5 Step source Grounded handbook content; LLM phrases only
    6 When to enter troubleshoot All CreateTicket candidates when KB enabled — no category allow-list
    7 Agency model Agent guides; user takes actions — agent never remediates
    8 Chat history in ticket Full transcript (redacted), not summary
    9 Multi-tenancy Column ready; single-org behavior in MVP
    10 Object storage Ceph RGW only — dedicated agent-handbooks bucket; no MinIO for KB

    17. Risks and mitigations¶

    Risk Impact Mitigation
    Hallucinated fixes Wrong advice Grounding rule; cite chunks; escalate if ungrounded
    Poor PDF conversion Bad steps / broken structure Docling + admin Markdown preview before publish; converter version pinned
    User thinks agent “did” something Confusion / unsafe assumptions Explicit copy: “Please try this… then tell me the result”
    Stale handbooks Bad L1 guidance Publish workflow; owners per doc
    Endless troubleshoot loops Poor UX Max steps/turns; always allow ticket creation
    Full transcript size / PII Provider limits; privacy Redaction; truncate oldest only as last resort; audit access
    Embedding cost / latency Slow chat Cache query embeddings per turn; small top-k
    Ceph outage Admin upload / reindex fails; runtime retrieve still works if Qdrant warm Runtime retrieve uses Qdrant, not Ceph; alert on ingest failures
    Qdrant outage Troubleshoot unavailable Fail open to CreateTicket with note; alert ops
    Admin exposed via chat auth Unauthorized KB edits Admin routes accept Keycloak Bearer only; reject X-User-Id
    Keycloak outage Admin unavailable Fail closed for admin; chat unaffected

    18. Out of scope (this strategy)¶

    • Replacing Zammad with a knowledge-only bot
    • Fully autonomous remediations (AD unlock, Intune actions) — separate runbook-executor strategy
    • Public internet-facing handbook portal
    • Training a custom LLM on handbook text
    • Automatic generation of handbooks from closed tickets (future content ops)
    • Category allow-list gating of troubleshoot entry
    • MinIO (or any non-Ceph stand-in) for Agent Handbook object storage
    • Chunking raw PDF without Markdown conversion
    • Marker / proprietary cloud OCR as the primary converter (Docling is locked)

    20. Success criteria for MVP¶

    1. Operator signs into Admin via Keycloak; users without kb_editor / kb_admin cannot call admin APIs.
    2. Operator can upload a PDF or Markdown handbook to Ceph RGW via Admin; PDFs are converted to Markdown with Docling; operator can publish (kb_admin).
    3. Chunks appear in Qdrant (from Markdown); admin retrieval preview returns the expected article.
    4. With KB_RAG_ENABLED=true, a VPN-style chat retrieves the handbook and presents at least one step for the user to perform.
    5. User saying the issue is fixed → no Zammad ticket; deflection event recorded.
    6. User saying it still fails → ticket created; description contains problem, handbook consulted, steps presented / user outcomes, and full conversation transcript (redacted).
    7. Troubleshoot runs for CreateTicket candidates without category allow-list gating.
    8. With flag off, existing CreateTicket / CheckStatus behavior unchanged.
    9. Chat continues to work without Keycloak; admin fails closed if Keycloak is down.
